**Implemented and deployed:**

- **AuditLog cross-org actor defect (schema tasks 5/6, plan §2.10) — fully fixed.** `PlatformAuditLog` gained a nullable `targetOrganizationId` (SetNull on target-org deletion, so history survives a deleted tenant same as `actorUserId` already survives a deleted actor). `PlatformTenantsService` (create/updateStatus/reissueOwnerInvite) and `EntitlementsService.setTenantModules` — the only two write paths that ever produced a cross-org row, both Super-Admin-only — now write to `PlatformAuditService` with `targetOrganizationId` instead of the target tenant's own `AuditLog`. The 18 existing bad rows were moved (not deleted — inserted into `PlatformAuditLog` with the same action/metadata/createdAt, then removed from `AuditLog`) by a one-off script, then deleted from the repo. A hand-written Postgres trigger (`auditlog_actor_same_org`, migration `20260905223040_...`) now rejects any INSERT/UPDATE on `AuditLog` where `userId` doesn't belong to `organizationId` — verified live by attempting exactly that insert and confirming rejection. A composite *foreign key* was deliberately not used here: `AuditLog.organizationId` is required, but `OrgService.removeMember` hard-deletes `User` rows and must still be able to `SET NULL` only `userId` — a composite FK's `ON DELETE SET NULL` would null both columns and violate the NOT NULL constraint. The trigger gets the same invariant without that conflict, following the same "Prisma can't express this" hand-written-migration convention as `RoomReservation`'s exclusion constraint.
- **`DesignDraft` uniqueness (schema task 3, plan §2.4) — fixed.** `documentId` (client-generated, so not trustworthy as a global key) is no longer globally `@unique`; the constraint is now `@@unique([organizationId, documentId])`. `DesignsService.putDraft` no longer needs its manual post-lookup ownership check (`existing.organizationId !== orgId` → 404) — the compound-key upsert can't resolve to another org's row by construction, so the check was removed rather than kept as dead code.
- Migration `20260905223040_p5a_platform_audit_targets_and_design_draft_scope` applied; `lumina-api-1` rebuilt/redeployed 2026-09-05. No dashboard changes.
- **Schema task 4: `PairingSession` model + `Screen.organizationId NOT NULL` (plan §2.4, §5.4 task 4) — done 2026-09-06.** `POST /player/init` (`PlayerService.requestPairingCode`) now creates a `PairingSession` row (no `organizationId` — it's a claim ticket, never tenant data) instead of a durable, tenant-nullable `Screen`. `ScreensService.confirmPairing` splits into two paths on the same pairingCode keyspace: `claimNewScreen` (a `PairingSession` match) creates the real `Screen` — already tenant-owned — inside a transaction that also deletes the session, reusing the session's `id` as the new Screen's `id` so the `screenId` the player already polls with, and the `sub` its eventual JWT carries, never change (no client-visible change for the web or Flutter player); `claimExistingScreen` is the pre-existing re-pair flow (`ScreensService.unpair` reissuing a code on an already tenant-owned row), now judged against a new `Screen.pairingCodeIssuedAt` column rather than `createdAt` — **this also fixes a real regression introduced earlier in this same pass**: task 11's TTL check had compared against `screen.createdAt` (the row's original creation time, which never changes across unpair/re-pair cycles), which would have made every re-pair code on a screen older than 15 minutes read as instantly expired the moment it was issued, permanently breaking the unpair→re-pair flow for every real screen. `unpair()`'s pairingCode collision-avoidance loop, and `requestPairingCode`'s own, now check both `Screen.pairingCode` and `PairingSession.pairingCode` — both live in the same keyspace so `confirmPairing` can resolve a code unambiguously. `apps/worker`'s `pairing-cleanup.service.ts` now reaps expired `PairingSession` rows (was: unowned `Screen` rows, which can no longer exist) and additionally clears stale re-pair codes off `Screen` rows past TTL (hygiene, not a security fix — `confirmPairing` already rejected them). Migration `20260906213254_p5a_pairing_session_and_screen_org_not_null` includes a defensive `DELETE FROM "Screen" WHERE "organizationId" IS NULL` immediately before the `NOT NULL` is applied, in case any accumulated between the 2026-09-05 audit's cleanup and this migration actually running. `lumina-api-1`/`lumina-worker-1` rebuilt and redeployed 2026-09-06; verified live (`POST /v1/player/init` → row lands in `PairingSession`, not `Screen`; `GET /v1/player/check` resolves it correctly) directly against the container wired to `docker-compose.prod.yml` (`lumina-postgres-1` — not the `lumina_postgres`/port-5435 container `apps/api/.env` points `DATABASE_URL` at for host-side tooling, which is a separate, explicitly-dev-only Postgres per `docker-compose.dev.local.yml`'s own comment; that instance was also migrated, harmlessly, as a side effect of running `prisma migrate deploy` from the host to generate/review the migration before building the image).

- **Schema tasks 1/2/7: composite tenant FKs across the plan's full relation list — done 2026-09-06.** Added `organizationId` to every child table on the plan's list that lacked one (`Zone`, `PlaylistItem`, `Floor`, `Poi`, `RouteNode`, `RouteEdge`, `KioskLocation`, `RoomDisplayBinding`, `RoomReservation`), each backfilled through its verified parent path in dependency order (`Building`→`Floor`→`Poi`/`RouteNode`→`RouteEdge`; `Layout`→`Zone`; `Playlist`→`PlaylistItem`; `Screen`→`KioskLocation`; `BookableRoom`→`RoomDisplayBinding`/`RoomReservation`) — every backfill derives from an already-`NOT NULL`, already-FK-enforced parent column, so none could leave a row unmatched. `DesignAssetVersion` was deliberately excluded: it has only one FK (`designAssetId`, required, cascade) with no second reference to cross-check against, so a same-tenant invariant there would be pure redundancy, not a real protection.

  Plain Postgres composite foreign keys were deliberately not used for the invariants themselves (schema task 2's actual goal) — every real candidate relation either (a) references a legitimately shared parent (`Asset`/`Theme`/`PoiCategory`, `organizationId IS NULL` for a platform preset), which a composite FK can only match exactly, never "match or is shared," or (b) uses `ON DELETE SET NULL` on the FK column, where a composite FK's `SET NULL` would null the row's own `organizationId` too and fail its `NOT NULL` constraint — the exact conflict `AuditLog` already hit (plan §2.10). Instead, 15 hand-written Postgres trigger functions (`check_<table>_tenant_refs`, one per table, each covering every cross-reference that table carries) run `BEFORE INSERT OR UPDATE` and reject a mismatch — same convention as `AuditLog`'s `check_auditlog_actor_same_org` trigger, extended to every table in the plan's list: `Screen` (playlistId/emergencyPlaylistId/assetId/groupId), `Schedule`, `PowerSchedule`, `Zone`, `PlaylistItem`, `Floor`, `Poi`, `KioskLocation`, `RouteNode`, `RouteEdge`, `RoomDisplayBinding`, `RoomReservation`, `BookableRoom` (wayfindingPoiId — the plan's own named schema-task-5 target, now checkable directly against `Poi.organizationId` instead of a floor/building join), `DesignAsset` (thumbnailAssetId). A bonus 15th trigger, flagged by the pre-migration audit's own bonus check but not itself in the plan's list, closes the inverse case: `DesignTemplate.thumbnailAssetId` (platform content, no `organizationId` of its own) must reference a *shared* asset, never a tenant-owned one — otherwise a template visible to every tenant could leak a reference to one specific tenant's private asset.

  Verified directly against real data (not just unit tests): a deliberate cross-tenant `UPDATE "Screen" SET "playlistId" = <another org's playlist>` was rejected by `check_screen_tenant_refs` with the expected error, and assigning a shared (`organizationId IS NULL`) asset to a screen succeeded, both run directly against Postgres. Every application service that creates a row in one of the 9 newly-non-nullable tables was updated to populate `organizationId` (`LayoutsService`, `PlaylistsService`, `PoisService`, `RoutesService`, `BuildingsService.createFloor`, `ScreensService.setKioskLocation`, `RoomBookingService` (both `updateDisplayBinding` and `bookNow`), `NativeCalendarProvider.createReservation`, the worker's `RoomBookingReconciliationService` (Microsoft 365 sync), and `seed-wayfinding.ts`/`seed-module-demos.ts`) — caught by `tsc`, since every one of these columns is a required Prisma field with no default. `ProviderRoomRef` (the room-calendar-provider interface) gained an `organizationId` field so both the native and future external providers can populate it. Migration `20260906215405_p5a_composite_tenant_fks`; `lumina-api-1`/`lumina-worker-1` rebuilt and redeployed 2026-09-06 — both came up with zero restarts, and real production traffic (a live dashboard session on `/en/wayfinding`) served correctly immediately after.

- **Operational finding, not a P5a task:** `lumina-worker-1`'s cron jobs (`fleet-monitor`, `pairing-cleanup`, `connectors`, `room-booking-renewal`) produced **zero log output** for 30+ minutes across many due firings, both before and after a clean container restart, despite the underlying service logic and DB connectivity both verified correct via direct invocation outside the container. Inconclusive after a bounded investigation (connection-pool gaps make "no idle DB connection" weak evidence either way, and `FleetMonitorService`/others are silent-by-design when there's nothing to report) — flagging for the next person to watch rather than continuing to consume turns on it. Worth a longer-horizon check: does a *new* abandoned pairing attempt actually get cleaned up on its own 15+ minutes later, without manual intervention?

## P7 status — done (2026-09-07)

**Goal:** `customerList`/`customerGet`/`createDesign` used to read `DesignTemplate.designJson` directly — the same row `adminUpdate` keeps mutating after publish — so an admin edit made after publish was instantly customer-visible, and nothing stopped `adminPublish` from snapshotting a designJson that embedded a tenant-private `assetId`, which a GLOBAL/SELECTED_TENANTS template would then leak to every authorized tenant.

**Implemented:**

- **`DesignTemplate.publishedVersionId`** (new, `@unique`, `onDelete: SetNull`) points at the `DesignTemplateVersion` snapshot `adminPublish` creates. Migration `20260907101544_p7_published_template_version_pointer` backfills it for any already-`PUBLISHED` row by matching `versionNumber` — safe because a template can only reach `PUBLISHED` through `adminPublish`, which has always bumped `versionNumber` and created the matching version row in the same transaction, so every backfill candidate has an exact match by construction. Dev database had zero `DesignTemplate` rows at migration time, so the backfill path itself is unexercised against real data — verified by SQL review and by the unit tests below instead.
- **`adminPublish`** now runs as one interactive `$transaction`, creates the version, then updates `status`/`versionNumber`/`publishedVersionId` together — the pointer can never point at a stale or missing version.
- **`customerGet`** now `include`s `publishedVersion` and returns *its* `designJson`/`schemaVersion`/`versionNumber`, never the live template row's. `customerList` gained a defensive `publishedVersionId: { not: null }` filter alongside the existing `status: 'PUBLISHED'` check (redundant by construction, kept as defense-in-depth — a template must never be customer-resolvable without an immutable version to point at).
